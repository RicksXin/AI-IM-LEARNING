LearningAI IM Backend

服务端系统是如何运作的

这个 server 是一个 Go + Gin 的 playground 服务端，负责给前端练习会话列表、短信/密码登录、JWT 个人资料请求、普通 WebSocket、认证聊天室 WebSocket 等基础能力。认证用户数据默认可以先走内存；配置 MySQL 后，可以通过 goose migration 把账号、资料、凭据、验证码持久化到正式的四表模型。

启动流程

服务端入口在 main.go。启动时先读取配置，再创建 Gin 路由，打印本机可访问地址，最后监听端口。

1. loadServerConfig 从环境变量读取 HOST、PORT 和 MySQL 配置，默认监听 0.0.0.0:8080。
2. setupRouter 创建 Gin Engine，挂载日志和恢复中间件，然后注册 HTTP 与 WebSocket 路由。
3. printAccessURLs 打印 localhost 和本机局域网 IPv4 地址，方便 iOS、Android、浏览器联调。
4. router.Run 开始监听请求，服务端进入持续运行状态。 
cd server
go run .

# 指定端口
PORT=8090 go run .

# 指定绑定地址
HOST=127.0.0.1 PORT=8080 go run .

# 使用本项目 Docker MySQL 持久化
DB_HOST=127.0.0.1 DB_PORT=3307 DB_USER=root DB_PASSWORD=flash_im_pwd DB_NAME=flash_im go run .

# 推荐：启动前先执行 goose migration
../scripts/database/start_server_with_mysql.sh

文件职责

main.go 程序入口，只负责加载配置、创建路由、打印访问地址和启动服务。
config.go 读取环境变量并生成监听地址和 MySQL DSN，支持 HOST、PORT、DB_* / MYSQL_*。
auth_mysql_store.go 实现 MySQL 认证仓库，读写 accounts、user_profiles、auth_credentials、sms_codes，并处理 bcrypt 密码校验。
router.go 集中注册所有路由，是理解服务端能力清单的第一入口。
version.go 实现 GET /v，返回服务名称和版本号。
conversation.go 实现 GET /conversation，返回模拟会话列表。
auth.go 实现短信验证码、密码登录、JWT 生成/解析、用户资料查询、密码设置/修改和内存用户仓库。
ws.go 实现简单 WebSocket 练习接口 /ws，连接后欢迎，收到文本后 echo。
chat_room.go 实现认证聊天室 /chat_room，客户端先用 JWT 鉴权，之后可以 ping/pong 和广播聊天消息。
network.go 扫描本机网卡并打印可访问 URL，解决模拟器和真机联调时不知道 IP 的问题。
main_test.go 覆盖版本、会话、认证、普通 WebSocket、认证聊天室等核心流程。

路由与接口

所有路由都在 router.go 中注册。HTTP 路由直接返回 JSON；WebSocket 路由会先把 HTTP 请求升级为长连接。

方法 路径 处理函数 用途
GET /v handleVersion 返回服务名和版本号，用于确认服务是否启动。
GET /conversation handleConversations 返回模拟会话列表，供前端 conversation playground 展示。
POST /auth/sms handleSendSMS 生成六位验证码；内存模式写入 map，MySQL 模式写入 sms_codes。
POST /auth/login handleLogin 支持短信登录和密码登录，登录成功后返回 JWT token、user_id、account_id、密码状态和设置密码引导标识。
GET /auth/profile handleUserProfile 正式个人资料接口，从请求头 token 解析 user_id，返回用户资料。
POST /auth/password/setup handlePasswordSetup 短信登录用户首次设置登录密码，需要携带 JWT。
PUT /auth/password handlePasswordChange 已设置密码用户修改密码，需要携带 JWT 和旧密码。
GET /user/profile handleUserProfile 兼容旧客户端的 profile 路由，行为与 /auth/profile 一致。
GET /ws handleWebSocket 普通 WebSocket 练习接口，连接欢迎，消息 echo。
GET /chat_room handleChatRoomWebSocket 带 JWT 鉴权的聊天室 WebSocket。
GET /chat_room/status chatRoomEndpointStatus 返回聊天室端点状态，方便快速确认接口存在。

认证系统

认证逻辑集中在独立模块 modules/flash_auth。目前支持两种登录方式：短信验证码登录和密码登录。两种登录方式最终都会得到同一种登录结果： token、user_id、account_id，以及 has_password / should_set_password。

短信验证码登录

  1. 客户端调用 POST /auth/sms，传入手机号。
  2. 服务端生成六位随机验证码，保存到 flash_auth 模块当前使用的认证存储中。
  3. 客户端调用 POST /auth/login，传入 login_type: "sms"、手机号和验证码。
  4. 服务端校验验证码。通过后，如果手机号不存在，就自动注册用户。
  5. 服务端生成 JWT，并把 token 返回给客户端。

密码登录

密码登录用于 playground 快速体验。服务端启动时会内置几个内存账号：

手机号 密码 昵称
13800000001 im123456 Alice
13800000002 chat123456 Bob
13800000003 demo123456 Demo User 
{
  "phone": "13800000001",
  "password": "im123456",
  "login_type": "password"
}

JWT 的作用

JWT 是“登录成功后的身份凭证”。服务端在 flash_auth.GenerateJWTForUser 中把 user_id、签发时间、过期时间、签发方写入 claims，然后用 HS256 和服务端密钥签名。 客户端后续请求 /auth/profile、兼容路由 /user/profile 或连接认证聊天室时，需要携带这个 token。

登录成功 服务端确认手机号和验证码/密码正确。
生成 token JWT claims 里写入 user_id 和过期时间。
客户端保存 前端保存 token，后续请求自动携带。
服务端解析 服务端验签并取出 user_id，再查询认证仓库。
当前 JWT 密钥仍然写在代码里，只适合 playground。MySQL 模式下密码会用 bcrypt 哈希保存；正式项目还需要把 JWT 密钥放到环境变量或密钥管理系统，并增加刷新 token、设备会话和审计日志。

MySQL 持久化

服务端现在支持两种认证存储模式：未配置数据库时使用 flash_auth.MemoryStore，适合快速测试；配置 MySQL 后使用 flash_auth.MySQLStore。推荐通过 scripts/database 下的脚本先执行 goose migration，再启动服务。服务端自身也保留了幂等建表能力，方便 playground 快速启动。

配置项 示例 说明
DB_NAME / MYSQL_DATABASE flash_im 设置后启用 MySQL 模式。服务会尝试 CREATE DATABASE IF NOT EXISTS。
DB_HOST / MYSQL_HOST 127.0.0.1 MySQL 主机地址，Docker 本地端口映射时通常是 127.0.0.1。
DB_PORT / MYSQL_PORT 3307 MySQL 端口。本项目 Docker 容器默认映射到宿主机 3307。
DB_USER / MYSQL_USER root 数据库用户名。
DB_PASSWORD / MYSQL_PASSWORD your_password 数据库密码。
DB_DSN / MYSQL_DSN root:flash_im_pwd@tcp(127.0.0.1:3307)/flash_im?parseTime=true 完整 DSN。提供 DSN 时优先使用它，不再自动创建数据库。 
cd server
DB_HOST=127.0.0.1 \
DB_PORT=3307 \
DB_USER=root \
DB_PASSWORD=flash_im_pwd \
DB_NAME=flash_im \
go run .

数据库结构由 server/migrations 下的 SQL 文件维护，脚本会自动检测并安装 goose。

# 查看迁移状态
./scripts/database/database_status.sh

./scripts/database/start_server_with_mysql.sh

认证数据表

  • accounts：账号主体，保存稳定身份 id、账号编号和账号状态。
  • user_profiles：用户展示资料，和 accounts 保持 1:1，保存昵称、头像、签名。
  • auth_credentials：登录凭据，和 accounts 保持 1:N，当前使用 credential_type = phone、identifier = 手机号，密码哈希保存在 secret_hash。
  • sms_codes：短信验证码，保存验证码、过期时间和消费时间；正式 IM 产品更常见放 Redis 并设置 TTL。
默认密码账号仍然可用：13800000001 / im123456、13800000002 / chat123456、13800000003 / demo123456。MySQL 模式下这些密码会以 bcrypt 哈希写入数据库。

WebSocket 系统

/ws 普通练习端点

这是最小 WebSocket 示例。连接建立后服务端发送欢迎消息 welcome to websocket playground。客户端发送文本后，服务端回复 echo: 原始消息。

它不要求登录，适合验证“浏览器或 RN 能不能成功建立 WebSocket 连接”。

/chat_room 认证聊天室

这是更接近 IM 产品的端点。连接建立后，服务端不会立刻允许聊天，而是先要求客户端发送 JWT 认证消息。 认证通过后，连接会加入聊天室 hub。

任意客户端发送 chat 消息后，服务端会广播给当前所有已认证连接。

认证聊天室通信流程

1. 建立连接 客户端连接 ws://host:port/chat_room。
2. 要求认证 服务端返回 auth_required。
3. 发送 token 客户端发送 {"type":"auth","token":"JWT"}。
4. 加入聊天室 服务端解析 token，成功后 register 到 hub。
5. 心跳 客户端发送 ping，服务端回复 pong。
6. 发消息 客户端发送 {"type":"chat","content":"你好"}。
7. 广播 hub 遍历已认证连接，把消息发给所有客户端。
8. 断开清理 连接关闭或写入失败时，从 hub 中移除客户端。 
// 客户端认证消息
{
  "type": "auth",
  "token": "jwt-token"
}

// 客户端聊天消息
{
  "type": "chat",
  "content": "hello"
}

// 服务端广播消息
{
  "type": "chat",
  "user_id": "u_000001",
  "nickname": "Alice",
  "content": "hello",
  "time": "15:04:05"
}

内存状态与并发保护

未配置 MySQL 时，认证数据会存放在进程内存里，服务重启后验证码、自动注册用户都会丢失。配置 MySQL 后，账号、用户资料、登录凭据和验证码会落库；WebSocket 连接仍然只存在于当前进程内存中。

authMemoryStore

  • smsCodes：手机号到验证码的映射。
  • usersByID：user_id 到用户信息的映射。
  • usersByPhone：手机号到用户信息的映射。
  • passwordsByPhone：未配置数据库时的 playground 密码映射。
  • mu：读写锁，避免并发请求同时读写 map 出错。

chatRoomHub

  • clients：当前已认证 WebSocket 客户端集合。
  • register：认证成功后加入集合。
  • unregister：断开连接或广播失败后移除。
  • broadcast：复制连接列表后逐个发送，避免长时间持有 hub 锁。
  • chatRoomClient.mu：保护单个 WebSocket 连接写入，避免并发写。
Go 的 map 不是并发安全的，所以内存 auth store 和 chat_room 都用锁保护共享状态。MySQL 模式下，认证数据交给数据库保证持久化和约束；聊天室连接集合仍然由内存 hub 管理。

本地网络与模拟器访问

HOST 默认是 0.0.0.0，表示监听本机所有网卡；PORT 默认是 8080。服务启动后，network.go 会打印 localhost 和局域网 IP 对应的访问地址。

环境 推荐访问地址 说明
Mac 本机浏览器 http://127.0.0.1:8080 浏览器和服务端在同一台机器上。
iOS 模拟器 http://127.0.0.1:8080 iOS 模拟器通常可以直接访问 Mac 的 localhost。
Android 模拟器 http://10.0.2.2:8080 Android 模拟器中的 localhost 指模拟器自己，访问宿主机要用 10.0.2.2。
真机 http://局域网IP:8080 手机和电脑需要在同一网络，使用服务启动时打印的局域网地址。

测试与验证

服务端测试集中在 main_test.go、auth_store_contract_test.go 和 auth_password_test.go，使用 httptest 验证 HTTP 接口，用 gorilla/websocket 验证 WebSocket 行为。 

cd server
go test ./...

测试覆盖的关键行为

  • /v 返回正确服务名和版本。
  • /conversation 返回 20 条模拟会话。
  • /ws 连接后欢迎，收到文本后 echo。
  • 短信登录可以生成验证码、登录、获取 profile。
  • 密码登录可以使用内置账号登录并获取 profile。
  • 短信登录用户可以首次设置密码，重复设置会被拒绝。
  • 已设置密码用户可以用旧密码修改密码，旧密码错误会被拒绝。
  • 无效验证码、无效密码、缺失 token、无效 token 会被拒绝。
  • /chat_room 必须先认证，认证后支持 ping/pong 和消息广播。

当前边界与后续演进

这个服务端是学习阶段的 playground，优点是简单、可读、容易联调；限制是很多能力还不是生产级。

当前边界

  • MySQL 目前只覆盖认证相关数据，聊天室消息仍不落库。
  • JWT 密钥硬编码在代码里。
  • 内存模式下默认账号仍是 playground 练习数据；MySQL 模式下密码已使用 bcrypt 哈希。
  • WebSocket origin 目前全部放行。
  • 聊天室消息不落库，没有历史消息和消息序列号。
  • 没有连接限流、设备管理、刷新 token、离线推送。

生产化方向

  • 引入数据库保存用户、会话、消息、成员关系。
  • 密码加盐哈希，JWT 密钥走环境变量或密钥管理。
  • 拆分 cmd/server 与 internal/auth、internal/chatroom 等包。
  • WebSocket 增加网关层、心跳超时、重连恢复和消息 ACK。
  • 消息由服务端生成 ID、序列号和时间，保证多端一致。
  • 增加结构化日志、指标监控、错误追踪和压测。
学习时先理解“HTTP 登录拿 token，WebSocket 连接后用 token 认证，认证成功再进入实时通信”这条主线。后续所有 IM 复杂能力，基本都是围绕这条主线继续扩展。
