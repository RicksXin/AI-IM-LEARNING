即时通信产品用户认证系统基础概念梳理

认证系统的任务不是“让用户填个账号密码”这么简单，而是回答三个连续问题：你是谁、你现在是否仍然可信、你能做什么。对 IM 产品来说，认证还要延伸到设备登录、长连接鉴权、断线重连、踢下线和多端同步。

场景：即时通信产品 主题：认证基础概念 重点：Token + 设备 + WebSocket 日期：2026-05-22

一、一句话理解认证

认证 Authentication：确认“你是谁”。例如用户输入手机号和验证码，服务端确认这个手机号确实属于你。
鉴权 Authorization：确认“你能做什么”。例如你可以看自己的会话，但不能看别人的会话。
账号 用户在系统里的身份入口，比如手机号、邮箱、用户名或第三方账号。
凭证 证明“我是我”的材料，比如密码、短信验证码、指纹、设备密钥。
Token 登录成功后的通行证，后续请求不用每次都提交密码。
会话 服务端对“这个用户当前登录状态”的记录，常和设备、Token、过期时间绑定。

二、认证系统里最容易混淆的概念

概念 通俗解释 在 IM 产品里的例子
用户 User 真实使用产品的人，系统里一般有一个稳定的 user_id。 小明注册了账号，系统给他分配 u_10001。
账号 Account 用户登录系统的入口，可以是手机号、邮箱、用户名或第三方账号。 小明用手机号登录，也可以绑定微信登录。
凭证 Credential 证明账号归属的材料。密码、验证码、Passkey、指纹都可以是凭证。 输入短信验证码，证明这个手机号当前由小明控制。
认证 Authentication 验证凭证是否正确，从而确认“你是谁”。 服务端验证验证码正确，确认请求者是小明。
鉴权 Authorization 判断一个已认证用户是否有权限做某件事。 小明能打开自己的会话，不能读取另一个用户的私聊。
Session 服务端保存的一段登录状态，通常和用户、设备、过期时间相关。 小明的 iPhone 有一个登录会话，Mac 也有另一个登录会话。
Access Token 短期通行证，用来访问 API 和建立 WebSocket。过期时间应较短。 请求 /conversation 时带上 Access Token。
Refresh Token 长期换票凭证，用来换新的 Access Token。泄露风险更高，应更谨慎保存。 App 打开后发现 Access Token 过期，用 Refresh Token 换一个新的。
Device 登录设备。IM 产品通常要知道“用户在哪台设备上在线”。 同一个用户同时在手机、平板、电脑在线。
WebSocket 鉴权 建立长连接时也要证明身份，否则服务端不知道这个连接属于谁。 连接 /ws 时携带 Access Token，服务端验证后绑定 userId 和 deviceId。

三、为什么 IM 认证比普通网站更特殊

1. 认证不只发生在 HTTP 请求

普通接口可以在请求头里带 Token；IM 还需要在 WebSocket 建连时认证。否则服务端无法知道这条长连接属于哪个用户、哪个设备。

2. 一个用户常有多个设备

手机、电脑、平板都可能同时在线。认证系统不能只记“用户已登录”，还要记录“哪台设备已登录”。

3. 断线重连必须能恢复身份

移动网络会切换。App 断线后重新连接时，需要重新证明身份，并根据游标补齐断线期间漏掉的消息。

4. 退出登录和踢下线要实时生效

如果用户改密码、注销设备或被风控踢下线，服务端应让对应 Token 或 Session 失效，并关闭相关 WebSocket 连接。

四、基础登录流程

登录流程可以理解成“拿临时通行证”。用户先提交凭证，服务端验证通过后签发 Token，并记录设备会话。

账号密码或验证码登录流程

sequenceDiagram
  participant U as "用户"
  participant App as "客户端"
  participant Auth as "认证服务"
  participant DB as "用户/会话存储"
  U->>App: "输入手机号 + 验证码或密码"
  App->>Auth: "POST /auth/login"
  Auth->>DB: "校验账号和凭证"
  DB-->>Auth: "校验通过"
  Auth->>DB: "创建设备会话 session"
  Auth-->>App: "Access Token + Refresh Token + userId + deviceId"
  App-->>U: "进入会话列表"
注意：登录成功后不要继续在客户端保存明文密码。后续请求应使用 Token，密码只在登录、改密、重新认证等必要场景出现。

五、HTTP 接口如何鉴权

登录后，客户端请求受保护接口时带上 Access Token。服务端验证 Token 有效、未过期、未被撤销，然后把请求映射到具体用户。

HTTP API 鉴权流程

sequenceDiagram
  participant App as "客户端"
  participant API as "HTTP API"
  participant Auth as "认证/会话校验"
  participant Biz as "业务服务"
  App->>API: "GET /conversation + Authorization: Bearer access_token"
  API->>Auth: "校验 Token"
  Auth-->>API: "userId、deviceId、权限信息"
  API->>Biz: "查询该用户的会话列表"
  Biz-->>API: "返回会话数据"
  API-->>App: "200 OK"

六、Access Token 和 Refresh Token 怎么配合

一个常见做法是：Access Token 有效期短，负责访问资源；Refresh Token 有效期更长，只负责换新 Access Token。这样即使 Access Token 泄露，攻击窗口也较短。

Token 类型 作用 生命周期 风险控制
Access Token 访问业务 API、建立 WebSocket。 短，比如 15 分钟、30 分钟或 2 小时，具体取决于安全要求。 过期快；服务端可验证签名、过期时间、撤销状态。
Refresh Token 换新的 Access Token。 较长，比如几天到几周。 只发给认证服务；应可撤销、可轮换、绑定设备。

Access Token 过期后的刷新流程

sequenceDiagram
  participant App as "客户端"
  participant API as "HTTP API"
  participant Auth as "认证服务"
  App->>API: "请求业务接口，Access Token 已过期"
  API-->>App: "401 Unauthorized"
  App->>Auth: "POST /auth/refresh + Refresh Token"
  Auth-->>App: "新的 Access Token，可选新的 Refresh Token"
  App->>API: "重试业务接口 + 新 Access Token"
  API-->>App: "200 OK"

七、WebSocket 建连也必须认证

WebSocket 一旦建立，就是一条长期存在的实时通道。服务端必须在连接建立阶段确认：这条连接属于哪个用户、哪个设备、哪个会话，否则无法安全地推送私聊消息。

WebSocket 认证与绑定连接

sequenceDiagram
  participant App as "客户端"
  participant WS as "WebSocket 网关"
  participant Auth as "认证/会话校验"
  participant Conn as "连接管理器"
  App->>WS: "连接 /ws，携带 Access Token"
  WS->>Auth: "校验 Token 和设备会话"
  Auth-->>WS: "userId + deviceId"
  WS->>Conn: "绑定 connectionId 到 userId/deviceId"
  WS-->>App: "连接成功"
  WS-->>App: "推送新消息、ack、已读、在线状态"
建议：playground 阶段可以先不做认证；进入真实 IM 阶段后，/ws 需要带 Token，并在服务端把连接绑定到用户和设备。

八、注册、登录、鉴权、退出的整体关系

如果把认证系统看成一张地图，可以分为注册、登录、访问资源、刷新 Token、退出登录几个动作。它们不是孤立接口，而是一套状态流转。

认证状态流转

flowchart LR
  Start["未登录"] --> Register["注册账号或绑定第三方账号"]
  Start --> Login["登录"]
  Register --> Login
  Login --> Session["创建用户设备会话"]
  Session --> Token["签发 Access Token 和 Refresh Token"]
  Token --> HTTP["访问 HTTP API"]
  Token --> WS["建立 WebSocket 实时连接"]
  HTTP --> Refresh{"Access Token 过期?"}
  Refresh -- "是" --> RefreshToken["使用 Refresh Token 换新 Token"]
  RefreshToken --> Token
  Refresh -- "否" --> HTTP
  Token --> Logout["退出登录 / 改密码 / 风控踢下线"]
  Logout --> Revoke["撤销 Token 和设备会话"]
  Revoke --> Start

九、IM 产品的认证数据模型可以先这样理解

对象 核心字段 作用
User id、nickname、avatar、status 表示一个用户主体，是会话、好友、消息的归属基础。
Account user_id、type、identifier 表示登录入口，比如手机号、邮箱、用户名、微信 OpenID。
Credential account_id、password_hash、verified_at 表示认证凭证。密码必须哈希存储，验证码只短期有效。
Device id、user_id、platform、device_name 表示登录设备，用于多端在线、推送、踢下线。
Session id、user_id、device_id、expires_at、revoked_at 表示一次登录态，用来判断 Token 是否还可信。
RefreshToken token_hash、session_id、expires_at、rotated_at 用于续期。建议服务端只存哈希，泄露后可撤销。
Connection connection_id、user_id、device_id、connected_at 表示 WebSocket 在线连接，用于实时推送和踢下线。

十、认证安全底线

  • 全程使用 TLS：登录、刷新 Token、WebSocket 都应该走安全传输；生产环境使用 https 和 wss。
  • 密码不要明文存储：只保存安全哈希，最好使用成熟算法和库。
  • 错误信息不要泄露账号存在性：登录失败时不要区分“账号不存在”和“密码错误”。
  • Access Token 短期有效：减少泄露后的可利用时间。
  • Refresh Token 可撤销、可轮换：退出登录、改密码、异常风险时要能让旧 Token 失效。
  • 设备会话要可管理：用户应能查看已登录设备，并主动退出某台设备。
  • 敏感操作需要重新认证：改密码、换手机号、删除账号、导出数据等不应只靠当前页面状态。
  • 记录认证日志：登录失败、刷新失败、异地登录、设备变更都应进入安全日志。

十一、给当前项目的分阶段建议

第一阶段：最小可用认证

  • 支持手机号或用户名登录。
  • 登录成功返回 accessToken、refreshToken、userId、deviceId。
  • HTTP API 通过 Authorization: Bearer accessToken 鉴权。
  • Refresh Token 支持续期和退出登录撤销。

第二阶段：接入 WebSocket 鉴权

  • /ws 建连时携带 Access Token。
  • 服务端校验后绑定 connectionId -> userId/deviceId。
  • Token 无效时拒绝连接或立即关闭连接。
  • 退出登录时关闭对应设备的 WebSocket 连接。

第三阶段：多端与安全增强

  • 支持设备列表、踢下线、改密码后全端退出。
  • 增加登录风险控制，例如频率限制、异常 IP、验证码。
  • 为敏感操作增加二次验证或 MFA。
  • 将认证日志纳入监控。

十二、总结

对 IM 产品来说，认证系统是整个消息系统的门禁。HTTP 接口要知道是谁在请求，会话列表和历史消息要按用户隔离；WebSocket 长连接要知道是谁在线，消息才能安全推送到正确设备。

最终建议：先做清楚“用户、账号、设备、会话、Access Token、Refresh Token”的边界，再让 HTTP API 和 WebSocket 网关都统一依赖这套认证结果。这样后续做多端登录、踢下线、离线推送和安全风控时，地基会稳很多。
