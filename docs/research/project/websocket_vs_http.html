IM Architecture Research

HTTP 与 WebSocket 对比：为什么 IM 产品必须使用实时长连接

HTTP 很适合做接口请求，但它天然是“客户端问，服务端答”。IM 的核心是“别人给你发消息时，服务端要立刻主动告诉你”。这个能力不能只靠普通 HTTP 请求优雅解决，在线实时通信必须引入 WebSocket 这样的长连接通道。

场景：即时通信产品 已有能力：HTTP 接口请求 新增能力：实时消息收发 结论：HTTP + WebSocket 组合使用

一、一句话结论

IM 产品不是完全抛弃 HTTP，而是必须把 HTTP 和 WebSocket 分工使用： HTTP 负责登录、拉取会话列表、历史消息、上传文件、配置查询；WebSocket 负责在线消息实时收发、服务端推送、已读回执、输入状态、在线状态和心跳保活。
HTTP 像打客服电话：你打过去问一次，对方回答一次。你不问，对方通常不会主动开口。
轮询 像每隔几秒问一次“有我的消息吗”。能用，但延迟、耗电、浪费请求。
WebSocket 像电话一直通着：双方都能随时说话，服务端可以立即把新消息推给客户端。
IM 用户期待消息“马上到”。只靠 HTTP 会让体验和成本都很难控制。

三、HTTP 和 WebSocket 的本质区别

对比项 HTTP WebSocket
连接方式 一次请求对应一次响应。请求结束后，这次业务交互就结束。 先通过 HTTP 握手升级，之后保持一条长连接。
通信方向 主要由客户端发起，服务端被动响应。 全双工通信，客户端和服务端都可以主动发送数据。
服务端主动推送 普通 HTTP 不擅长。通常要靠轮询、长轮询或额外推送服务绕开。 天然支持。服务端收到新消息后，可以立刻推给在线客户端。
实时性 取决于客户端多久请求一次。轮询间隔越长，消息越慢；间隔越短，成本越高。 消息可以在毫秒级到达在线客户端，体验接近实时。
请求开销 频繁轮询会反复携带请求头、Cookie、鉴权等信息，浪费流量和服务端资源。 握手后复用同一条连接，适合频繁、小包、双向事件。
适合业务 登录、REST API、列表、分页、搜索、上传下载、历史消息补拉。 实时消息、在线状态、输入中、已读回执、撤回通知、心跳、断线重连后的同步触发。
复杂度 简单、成熟、易缓存、易调试。 需要处理连接管理、鉴权、心跳、重连、消息确认、离线补偿。

四、通信流程差异

1. 普通 HTTP：客户端问一次，服务端答一次

HTTP 的模型很适合“我现在要一份数据”的场景。例如打开会话列表、拉取历史消息、提交登录表单。问题是：如果朋友在 3 秒后给你发了新消息，服务端不能凭空通过这次已经结束的 HTTP 请求再把消息塞回来。

普通 HTTP 请求响应

sequenceDiagram
  participant C as "客户端"
  participant S as "服务端"
  C->>S: "GET /conversation"
  S-->>C: "返回会话列表"
  Note over C,S: "请求结束，连接交互完成"
  S--xC: "后续新消息无法通过已结束请求主动推送"

2. HTTP 轮询：反复问“有没有新消息”

如果只用 HTTP 做 IM，常见补救办法是轮询：客户端每隔几秒请求一次 /messages/sync。这能勉强做出“似乎会更新”的效果，但体验和成本都不好。

HTTP 轮询新消息

sequenceDiagram
  participant C as "客户端"
  participant S as "服务端"
  loop "每 3 秒轮询一次"
    C->>S: "GET /messages/sync?cursor=100"
    alt "没有新消息"
      S-->>C: "空数组"
    else "有新消息"
      S-->>C: "返回新消息"
    end
  end
  Note over C,S: "间隔短：耗电耗流量；间隔长：消息到达慢"

3. WebSocket：连接保持，双方随时说话

WebSocket 的关键变化是：客户端登录后建立一条持续存在的连接。只要用户在线，服务端就能把新消息、回执、通知立即推过来。

WebSocket 长连接实时通信

sequenceDiagram
  participant A as "用户 A 客户端"
  participant G as "WebSocket 网关"
  participant B as "用户 B 客户端"
  A->>G: "连接 WebSocket 并携带 token"
  G-->>A: "鉴权通过，连接保持"
  B->>G: "连接 WebSocket 并携带 token"
  G-->>B: "鉴权通过，连接保持"
  A->>G: "发送消息：你好"
  G-->>A: "发送确认 ack"
  G-->>B: "实时推送新消息：你好"
  B->>G: "已读回执"
  G-->>A: "实时推送已读状态"
  Note over A,B: "双方在线时，消息和状态都能实时双向流动"

五、为什么 IM 产品必须用 WebSocket

1. 新消息必须由服务端主动推送

IM 的消息不是用户自己主动刷新出来的，而是别人随时发来的。用户 A 发消息给用户 B 时，B 可能什么都没点，服务端也必须立刻通知 B。

普通 HTTP 的问题：B 不请求，服务端就很难主动告诉 B。

WebSocket 的优势：B 在线时连接一直在，服务端可以直接推送。

2. 轮询会造成延迟和浪费

如果每 5 秒轮询一次，用户最多可能等 5 秒才看到消息；如果每 1 秒轮询一次，请求量、耗电和服务端压力都会上升。

普通 HTTP 的问题：实时性和成本之间很难平衡。

WebSocket 的优势：没有消息时不必反复请求，有消息时立即推送。

3. IM 不只有消息，还有很多实时状态

输入中、已读、撤回、在线状态、离线重连、对方正在录音，这些都是“小而频繁”的事件。它们用 HTTP 轮询会很笨重。

普通 HTTP 的问题：每种状态都可能变成一次请求或一次轮询。

WebSocket 的优势：同一条连接承载多种实时事件。

4. 发送、确认、补偿需要形成闭环

一条消息发出后，客户端需要知道服务端是否收到、是否落库、是否分配序列号、对方是否收到。WebSocket 更适合做连续的确认流程。

普通 HTTP 的问题：只能完成发送请求，后续状态变化仍要额外查询。

WebSocket 的优势：发送、ack、投递、已读可以在同一实时通道上完成。

六、推荐的 IM 通信分工

对 IM 产品来说，正确架构通常不是“HTTP 或 WebSocket 二选一”，而是明确分工：HTTP 管稳定的数据接口，WebSocket 管在线实时事件。

业务能力 推荐协议 说明
登录、注册、刷新 token HTTP 一次请求一次响应，语义清晰，容易调试。
拉取会话列表 HTTP 进入页面时初始化列表，适合分页、缓存和错误重试。
拉取历史消息 HTTP 按游标或分页加载，适合补历史、查记录。
上传图片、文件、语音 HTTP 大文件上传下载不建议塞进 WebSocket 主消息通道。
在线收新消息 WebSocket 服务端收到消息后立即推给在线用户。
发送消息和服务端 ack WebSocket 适合小包、频繁、连续的消息确认。
已读、撤回、输入中、在线状态 WebSocket 都是实时事件，适合同一条长连接承载。
后台离线提醒 APNs / FCM / 厂商推送 移动端退到后台后，系统可能限制长连接，需要系统推送补充。

七、只用 HTTP 做 IM 会遇到什么问题

  1. 消息到达不稳定：轮询间隔决定延迟，用户可能明显感觉慢半拍。
  2. 服务端压力浪费：大量用户在线但没有消息时，轮询仍会产生海量空请求。
  3. 移动端耗电耗流量：频繁唤醒网络对手机体验很不友好。
  4. 状态同步复杂：输入中、已读、撤回、在线状态都要另做查询或轮询。
  5. 消息确认链路割裂：发送、服务端确认、对端投递、已读状态无法自然串起来。
  6. 体验不符合用户预期：IM 用户默认期待“对方一发，我马上看到”。
关键判断： 如果一个产品的核心体验是“别人发生了动作，我这里要立刻知道”，那它就不能只依赖普通 HTTP 请求。IM、协同编辑、在线游戏、实时行情、直播互动都属于这类场景。

八、WebSocket 在 IM 中需要补齐的工程能力

WebSocket 解决的是实时通道问题，不等于自动解决 IM 的全部可靠性问题。真正的 IM 系统还需要在 WebSocket 之上设计消息协议和状态机。

能力 为什么需要 常见做法
连接鉴权 防止未登录用户建立实时通道。 连接时携带 token，服务端校验后绑定 userId、deviceId。
心跳保活 及时发现断线、弱网和假在线。 客户端定时 ping，服务端 pong；超时后断开并重连。
消息确认 ack 客户端要知道消息是否被服务端成功接收和落库。 客户端生成 clientMsgId，服务端返回 serverMsgId、conversationSeq。
断线重连 移动网络会频繁切换，连接不可能永远稳定。 指数退避重连，恢复后用 cursor 补拉缺失消息。
消息补偿 WebSocket 推送可能因为断网错过，不能只依赖在线推送。 保留 HTTP sync 接口，按会话序列号或全局游标补齐。
多端同步 一个用户可能同时登录手机、平板、电脑。 服务端维护用户多连接，消息和状态按设备或用户维度分发。

九、给当前项目的落地建议

第一阶段：保留现有 HTTP，新增 WebSocket playground

  • 继续用 HTTP 请求 /conversation 做会话列表初始化。
  • 新增 /ws 或 /gateway WebSocket 入口。
  • 在 React Native playground 中新增 WebSocket 连接测试页。
  • 先实现连接、鉴权、心跳、服务端主动推送测试消息。

第二阶段：定义 IM 消息协议

{
  "type": "message.send",
  "clientMsgId": "local-uuid",
  "conversationId": "c_1001",
  "payload": {
    "text": "你好"
  }
}

建议所有 WebSocket 包都带 type，这样后续可以扩展消息、ack、已读、撤回、输入中、心跳等事件。

第三阶段：HTTP 和 WebSocket 形成闭环

  • WebSocket 收实时消息。
  • HTTP 按 cursor 补拉断线期间漏掉的消息。
  • HTTP 拉历史和上传媒体。
  • WebSocket 推送实时状态和消息确认。

十、总结

HTTP 是接口请求的基础，稳定、简单、适合 CRUD 和批量数据获取；WebSocket 是在线实时通信的核心，适合服务端主动推送和频繁双向事件。IM 产品的核心体验是实时，因此不能只靠普通 HTTP。

最终建议： 当前项目应继续保留 HTTP 作为数据接口层，同时新增 WebSocket 作为实时消息通道。未来的 IM 架构应以「HTTP 初始化与补偿 + WebSocket 实时收发 + 系统推送兜底离线提醒」为主线推进。
