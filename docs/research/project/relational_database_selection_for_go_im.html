Database Research

Go 即时通信后端关系型数据库选型调研报告

当前认证系统把用户、验证码、密码账号都放在 Go 进程内存中，服务重启后数据会丢失。下一步要引入数据库持久化用户数据，本报告从功能、性能、生态、适用场景几个维度比较常见关系型数据库，并给出适合 Go IM 后端的建议。

生成日期：2026-06-09 项目阶段：playground → 持久化改造 重点对象：用户数据、登录凭证、关系数据、消息元数据

结论先行

推荐优先选择 PostgreSQL。 对一个正在成长中的 Go 即时通信后端来说，PostgreSQL 在事务一致性、复杂查询、索引能力、JSONB 扩展性、开源生态和 Go 驱动成熟度之间比较均衡。它适合先把用户、账号、好友关系、会话成员、消息索引等核心数据建模清楚，再逐步做读写分离、分区、归档和缓存。

当前阶段最佳选择

PostgreSQL：适合新项目、Go 后端、关系模型仍在演进、后续可能需要复杂查询和 JSON 扩展的 IM 产品。

首选

团队已有 MySQL 经验

MySQL：如果团队运维、云数据库、历史工具链都围绕 MySQL，选择 MySQL 也很稳。它的 OLTP 能力成熟，生态巨大。

可选

不建议现在上来就用

TiDB / CockroachDB：它们解决的是分布式 SQL、横向扩展、多地域一致性，能力很强，但运维和事务心智更复杂，适合规模明确增长后再评估。

后续评估

另外要明确一点：关系型数据库适合持久化“用户资料、账号、会话、成员关系、消息历史和消息索引”，但不应该承担所有 IM 实时能力。在线状态、连接路由、热点计数、临时验证码、消息投递队列，后续通常还会引入 Redis、消息队列、对象存储或搜索引擎。

IM 后端对数据库的核心诉求

用户与认证

  • 用户表、手机号唯一索引、昵称头像等基础资料。
  • 密码哈希、登录方式、账号状态、注册时间。
  • JWT 通常不落库，但刷新令牌、设备会话可以落库。

关系与会话

  • 好友关系、黑名单、群成员、会话成员。
  • 需要唯一约束、事务更新、分页查询。
  • 未来可能有多端同步和会话未读状态。

消息持久化

  • 消息写入量高，常按会话、时间、消息 ID 查询。
  • 需要分区、归档、冷热分层，避免单表无限膨胀。
  • 消息投递实时性不应完全依赖数据库轮询。

运维与扩展

  • 备份恢复、监控、慢查询分析、迁移工具。
  • 连接池、事务超时、索引治理、读写分离。
  • 先单主稳定，再考虑分布式数据库。

主流关系型数据库对比

数据库 功能能力 性能特点 Go 生态 适合场景 对本项目建议
PostgreSQL ACID、MVCC、丰富索引、分区、JSON/JSONB、全文检索、触发器、扩展体系。JSONB 可配合 GIN 索引做半结构化字段查询。 复杂查询、事务一致性、数据建模能力强；高写入场景需要关注索引数量、WAL、连接池和分区策略。 Go 中常用 pgx、database/sql 适配，迁移、ORM、查询构造器生态成熟。 新业务后端、复杂关系模型、需要事务一致性和查询表达力的系统。 首选。适合作为用户、会话、关系、消息元数据的主数据库。
MySQL InnoDB 支持事务、行级锁、MVCC、外键、JSON 函数、复制和成熟的主从/高可用方案。 OLTP、主键查询、高并发短事务表现成熟；复杂分析和半结构化查询表达力通常不如 PostgreSQL 顺手。 Go 中 go-sql-driver/mysql 使用广泛，云厂商托管产品、DBA 经验和工具链非常丰富。 团队已有 MySQL 经验、业务以简单 OLTP 为主、希望使用成熟托管 MySQL。 强可选。如果你更熟 MySQL，用它持久化认证和用户数据完全可行。
MariaDB MySQL 分支，兼容 MySQL 生态；Galera Cluster 提供近同步多主集群能力。 单机 OLTP 与 MySQL 类似；Galera 多主不是简单写扩展，所有节点都要应用写入，跨地域延迟会影响提交。 可复用大部分 MySQL 驱动和工具；但云厂商、企业支持和社区资料与 MySQL/PostgreSQL 相比略分散。 偏好开源 MySQL 分支、已有 MariaDB 运维基础、需要 Galera 高可用。 可选但不优先。除非团队已有 MariaDB 经验，否则不如 PostgreSQL/MySQL 清晰。
SQLite 嵌入式、单文件、零服务进程、支持事务。非常适合本地开发、测试、桌面端和小工具。 读取很快，部署简单；并发写入和多服务实例访问不是它的强项，不适合作为多实例 IM 后端主库。 Go 驱动可用，但生产服务端通常仍会选择 PostgreSQL/MySQL 这类独立数据库服务。 单机工具、开发测试、边缘端、本地缓存、小规模原型。 仅建议本地开发。不建议承担 IM 服务端正式用户主数据。
SQL Server 企业级 RDBMS，T-SQL、JSON 支持、In-Memory OLTP、Always On 可用性组、完善管理工具。 企业 OLTP 和报表场景成熟；授权、部署和 Windows/Microsoft 生态绑定需要纳入成本。 Go 可通过 SQL Server 驱动访问，但 Go 开源后端社区默认资料不如 PostgreSQL/MySQL 多。 公司已经重度使用 Microsoft/Azure/SQL Server，且有 DBA 和授权预算。 企业场景可选。绿色 Go IM 项目通常不作为首选。
Oracle Database 企业级能力强，Data Guard、RAC、备份恢复、安全审计、JSON 支持和复杂事务能力成熟。 大企业核心系统稳定性强，但成本、运维复杂度和学习曲线高。 Go 可接入，但相比 PostgreSQL/MySQL，开源项目资料、轻量部署和本地开发体验弱一些。 金融、电信、政企等已有 Oracle 体系，且对可用性、审计、容灾有强要求。 不建议新手阶段选择。除非组织已指定 Oracle。
TiDB MySQL 协议兼容、分布式 SQL、水平扩展、HTAP，支持乐观/悲观分布式事务。 适合超出单机 MySQL 的数据量或吞吐；分布式事务有网络和协调开销，小规模阶段成本偏高。 可复用 MySQL 协议和部分工具；但需要理解 TiDB/TiKV/PD 等分布式组件。 单机 MySQL 瓶颈明显、需要横向扩展和实时分析的中大型系统。 后期评估。当前只做用户持久化时过重。
CockroachDB PostgreSQL wire protocol 兼容、分布式 SQL、默认 Serializable 事务、多地域能力强。 一致性强，但事务冲突需要应用处理重试；跨地域写入延迟不可忽视。 可使用 PostgreSQL 协议驱动；但兼容性、SQL 特性和运维心智需要单独验证。 多地域、多活、高一致性要求明确，团队能接受分布式数据库复杂度。 后期评估。适合规模和多地域要求明确之后。

分维度分析

1. 功能维度

对 IM 后端来说，数据库最重要的不是“功能最多”，而是能稳定表达关系模型：手机号唯一、用户 ID 唯一、设备会话、好友关系、群成员、会话成员、消息索引等。PostgreSQL 和 MySQL 都能很好完成这件事。PostgreSQL 在 JSONB、索引类型、复杂 SQL、扩展体系上更灵活；MySQL 在简单 OLTP 和通用业务系统里非常成熟。

SQL Server 和 Oracle 功能都很强，但更像“企业平台选择”，不是轻量 Go IM 项目的自然起点。TiDB 和 CockroachDB 解决的是分布式 SQL 问题，适合当业务已经确认需要水平扩展、多地域或强一致分布式事务时再进入选型。

2. 性能维度

性能不能脱离表结构、索引、硬件、事务模式和查询模式直接排序。对于认证系统和用户资料，PostgreSQL/MySQL/MariaDB/SQL Server/Oracle 都远远够用；真正容易把数据库压垮的是消息历史、未读数、群成员大表、热点会话写入和不合理索引。

当前阶段更应该关注这些设计：用户 ID 使用稳定主键；手机号加唯一索引；消息表按会话或时间分区；列表查询走组合索引；不要把在线状态和每次心跳都写进关系型数据库。

3. 生态维度

Go 官方提供 database/sql 作为通用抽象，并通过驱动接入不同数据库。PostgreSQL 的 pgx、MySQL 的 go-sql-driver/mysql 都是 Go 项目常见选择。ORM 方面，GORM、sqlc、ent、bun 等也都对 PostgreSQL/MySQL 支持良好。

对本项目这种学习型 Go 后端，生态意味着：文档容易查、错误容易搜索、迁移工具多、云数据库托管成熟、本地 Docker 启动方便。PostgreSQL 和 MySQL 在这些方面都非常稳。

4. 适用场景维度

1

只是要把内存用户数据落库：PostgreSQL 或 MySQL。优先 PostgreSQL；如果团队已经熟悉 MySQL，就选 MySQL。

2

只是本地开发或单机 demo：SQLite 可以很舒服，但不要把它当多实例 IM 后端主库。

3

公司已有企业数据库体系：SQL Server 或 Oracle 可以顺应组织标准，但要接受授权和运维成本。

4

已经进入大规模、多地域、单机瓶颈阶段：再评估 TiDB、CockroachDB，或者做数据库分片、消息表归档和专用存储架构。

建议的阶段路线

第一阶段：认证与用户持久化

  • 选择 PostgreSQL。
  • 新增 users、auth_identities、sms_codes 或临时验证码存储。
  • 密码必须保存哈希，不保存明文。
  • Go 侧建立 repository 层，避免 handler 直接写 SQL。

第二阶段：会话与关系模型

  • 新增好友、群成员、会话成员表。
  • 所有关系变更放在事务里。
  • 为常用查询建立组合索引。
  • 把 WebSocket 在线状态放在 Redis，而不是关系型数据库。

第三阶段：消息持久化

  • 消息表按时间或会话做分区。
  • 服务端生成消息 ID、序列号和创建时间。
  • 热消息在主库，历史消息可归档或异步迁移。
  • 大附件放对象存储，数据库只存元数据。

第四阶段：规模化

  • 先做连接池、慢查询、索引治理、读副本。
  • 再考虑消息表拆分、冷热分层、CQRS。
  • 最后才是 TiDB/CockroachDB/分片等复杂方案。
  • 数据库选型要跟业务规模一起升级，不要提前背复杂度。

推荐的初始表方向

如果下一步开始落地 PostgreSQL，可以先从认证系统最小闭环开始，避免一次性把 IM 全部数据模型铺开。 

users
- id              用户主键
- phone           手机号，唯一
- nickname        昵称
- avatar          头像 URL
- created_at      注册时间
- updated_at      更新时间

auth_identities
- id
- user_id         关联 users.id
- login_type      sms/password
- identifier      phone/open_id/email 等登录标识
- password_hash   密码哈希，短信登录为空
- created_at
- updated_at

login_sessions 或 refresh_tokens
- id
- user_id
- token_hash
- device_id
- expires_at
- revoked_at
- created_at
验证码是否落关系型数据库要看产品需求。如果只是 60 秒短期验证码，更常见做法是放 Redis，并设置 TTL。关系型数据库可以先只保存用户和登录身份。

最终建议

  1. 当前项目建议选 PostgreSQL。它更适合作为 Go IM 后端的长期主库，能够覆盖认证、用户、关系、会话和消息元数据。
  2. 如果你或团队更熟 MySQL，也可以选 MySQL。MySQL 在互联网业务中非常成熟，持久化认证系统没有问题。
  3. 不要用 SQLite 做正式服务端主库。它适合开发测试和本地工具，不适合多实例实时 IM 后端。
  4. 不要过早引入分布式 SQL。TiDB/CockroachDB 很有价值，但当前阶段先把数据模型、事务边界、索引和 repository 分层做好，收益更大。
  5. 关系型数据库不是 IM 的全部。实时连接、在线状态、消息投递、推送、搜索、文件存储后续会拆到其他组件。
