Development Report

Conversation Playground AI 协作流程汇报

从一句聊天式需求开始，AI 完成技术栈澄清、请求层实现、视图层拆分、测试验证和运行说明，最终交付一个可运行、可配置、可测试、可展示的 React Native conversation playground。

日期：2026-05-21 客户端：React Native + TypeScript 请求库：axios 后端接口：GET /conversation

一、背景

本次任务从「在 playground 里做一个简单的网络请求单元，叫做 conversation」开始。用户主要通过聊天提出目标、补充约束和截图参考；AI 负责检查项目上下文、识别技术栈、澄清歧义、选择方案、编写代码、补测试、验证结果，并说明如何在 iOS 模拟器查看。

从 0 到 1 先完成 conversation 请求单元，再接入 playground，最后按截图实现会话列表视图。
结构分层 实体、配置、请求 client、API、容器、视图组件各自独立，减少后续迁移成本。
可独立验证 请求层支持注入 fake client，单元测试不依赖真实网络和后端服务。

二、最终产出

1. 请求单元

在 client/flash_im/src/playground/conversation 下新增 conversation 模块。

2. 会话视图层

根据用户截图，实现接近微信会话页的视图结构，并拆成更小的 UI 单元。

3. 测试覆盖

  • __tests__/conversationApi.test.ts：覆盖 baseURL 配置、axios client 配置、实体映射、接口请求和异常响应。
  • __tests__/conversationView.test.tsx：覆盖视图层关键内容与刷新行为。
  • __tests__/PlaygroundApp.test.tsx：确保 playground 首页暴露 conversation 入口。

三、关键流程点

1. 先识别技术栈，而不是直接套用用户词汇

用户最初提到「使用 dio 库」。AI 没有直接照做，而是先检查仓库，确认当前客户端是 React Native + TypeScript，后端是 Go，仓库中没有 Flutter/Dart 工程。

判断结果：dio 属于 Dart/Flutter 生态，不适合直接用于当前 RN 客户端。React Native 中更适合使用 fetch 或 axios。用户确认后，最终选择 axios。

2. 先看现有结构，再决定落点

AI 先读取了已有 playground、测试和后端接口文件，由此确认：

  • playground 已经是独立入口。
  • 当前已有案例组织方式是 src/playground/cases。
  • 后端已有 GET /conversation 接口，返回 title、lastMsg、time。
  • 测试使用 Jest 和 react-test-renderer。

3. 请求层和视图层分离

请求相关

entity config request client api

请求配置、接口路径、响应映射和 HTTP client 创建互相独立。

视图相关

screen header list row avatar tab bar

视图按截图中的视觉单元拆分，后续替换、迁移和扩展更轻松。

4. 用依赖注入保证接口可独立测试

ConversationApi 支持注入 client，测试中可以传入假的 client.get，不需要真实启动后端。

const api = new ConversationApi({ client });

这让 API 层测试稳定、快速，并且能精确断言请求路径是 /conversation。

5. 先做可联调，再做接近截图的体验

第一版 conversation 页面偏请求调试：可输入 Host/IP、Port，可点击按钮请求列表。用户提供截图后，AI 将视图重构为接近微信会话页，同时保留顶部联调配置条，兼顾「好看」和「能调接口」。

6. 每个阶段都做验证

  • 局部 Jest：只跑 conversation API、view 和 playground 入口测试。
  • 全量 Jest：确认其它测试没有被破坏。
  • TypeScript：执行 npx tsc --noEmit。
  • ESLint：执行 npm run lint。
  • npm audit --omit=dev：识别依赖安全提示。

最终结果：5 个测试套件通过，13 个测试通过，TypeScript 检查通过，ESLint 通过。

注意：npm audit 仍报告 7 个 moderate，来源是 React Native CLI 依赖链，不是 conversation 请求层新增逻辑本身。

四、AI 协作模式总结

  1. 用户描述目标：在 playground 中做 conversation 网络请求单元。
  2. AI 检查项目上下文，确认是 React Native 客户端和 Go 后端。
  3. AI 识别关键歧义：dio 与当前 RN 技术栈不匹配。
  4. AI 解释技术选型，用户确认使用 axios。
  5. AI 安装依赖，分层实现请求单元。
  6. AI 编写独立测试，验证配置、实体映射、API 调用和异常响应。
  7. AI 接入 playground 首页和页面入口。
  8. 用户提供截图，AI 根据截图重构视图层。
  9. AI 保持请求层、容器层、视图层分离。
  10. AI 运行测试、类型检查和 lint，并给出 iOS 模拟器运行方式。

这说明从 0 到 1 的功能搭建不一定需要用户逐条写需求。只要用户持续对话、确认方向并提供关键参考，AI 可以承担大部分工程执行工作。

五、可复用经验

  • 遇到技术名词先确认生态。例如 dio，不能脱离项目技术栈直接套用。
  • playground 功能也要有边界。demo 代码如果有清晰分层，后续就具备迁移价值。
  • 请求代码最好天然可测。通过注入 HTTP client，可以把真实网络从单元测试中拿掉。
  • 截图驱动 UI 时要拆视觉单元。header、list、row、avatar、tab bar 分开后更容易迭代。
  • AI 不只是写代码，也要负责验证。最终交付应包含能跑、能测、结构清楚的结果。

六、后续建议

1. 增加 iOS playground 启动脚本

当前 iOS DEBUG 入口已切到 index.playground，但更好的方式是增加类似 Android 的 playground 启动参数或 scheme，避免手动改 Swift 文件。

2. 增加真实头像字段

后端当前 conversation 只有 title、lastMsg、time。如果要更接近真实 IM，可以增加：

  • id
  • avatarUrl
  • unreadCount
  • isMuted
  • isPinned

3. 增加正式首页迁移路径

当 conversation 模块稳定后，可以将请求层和视图层迁移到正式 src/features/conversation 或类似目录，playground 保留为演示与联调用例。

4. 增加网络状态展示

后续可以补充首次加载状态、下拉刷新、空列表状态、请求失败重试和弱网超时提示。这些都可以在不破坏现有分层的基础上继续扩展。
